EXECUTIVE SUMMARY
═══════════════════════════════════════════════════════════════════════════════

SurplusSell is a production-grade B2B marketplace platform designed to connect 
construction material suppliers, contractors, and buyers in Ethiopia. The platform 
facilitates the buying, selling, and trading of surplus construction materials 
(cement, rebar, steel, lumber, aggregates, etc.) with built-in trust mechanisms, 
verification systems, escrow payments, and logistics coordination.

TARGET MARKET: Ethiopian construction industry (~$15B annual market)
PRIMARY USERS: Contractors, material suppliers, construction firms, developers
REVENUE MODEL: Transaction commission (5-8%), verification fees, subscriptions
COMPETITIVE MOAT: Verification agent network + escrow trust + price transparency

SECTION 1: PRODUCT ANALYSIS
═══════════════════════════════════════════════════════════════════════════════

1.1 IDEA ANALYSIS
─────────────────
CORE VALUE PROPOSITION:
- Reduce construction waste by reselling surplus materials
- Lower material costs for buyers (15-40% below retail)
- Generate revenue for sellers from idle inventory
- Create price transparency in Ethiopian construction market
- Enable cross-city material trading (Addis -> Hawassa, etc.)

MARKET OPPORTUNITY:
- Ethiopia's construction sector is ~15% of GDP
- ~30% of construction materials go unused or wasted
- No dominant digital marketplace exists (2Merkato is directory-only)
- SanduraCM is "coming soon" — first-mover advantage available
- ~50,000+ active contractors in Addis Ababa alone

1.2 MISSING FEATURES IN CURRENT MARKET
────────────────────────────────────────
- No escrow/payment protection for B2B transactions
- No verification of material quality/quantity
- No logistics coordination for heavy materials
- No price index/transparency
- No bulk dealer tools
- No multi-language support (Amharic, Oromiffa, Tigrinya)
- No offline capability for rural connectivity

1.3 WEAK POINTS & RISKS
────────────────────────
RISK                              | MITIGATION STRATEGY
─────────────────────────────────────────────────────────────
Trust deficit (scams)            | Verification agents + escrow + ratings
Payment fraud                    | Escrow only, no direct payments
Low digital literacy               | Simple UI, phone-based auth, Amharic-first
Logistics complexity              | Partner with trucking companies
Regulatory (NBE)                   | Start with manual reconciliation, partner later
Competition from 2Merkato          | Superior UX, escrow, verification
Network effect (chicken-egg)      | Free listings Phase 1, verification incentives
Data sovereignty (Ethiopian law)   | Host in Ethiopia, comply with ECA

1.4 INNOVATIVE FEATURES
────────────────────────
- AI Price Recommendation: Suggest listing prices based on market data
- Material Quality Scanner: AI-powered photo analysis for condition grading
- Smart Matching: Auto-suggest buyers for new listings based on preferences
- Bulk Import API: Allow large suppliers to upload inventory via CSV/API
- Construction Project Integration: Link listings to active project needs
- Carbon Credit Tracking: Quantify waste reduction for ESG reporting
- Voice Search: Amharic voice search for low-literacy users
- Offline Mode: Browse cached listings, queue actions for sync

2.1 ROLE DEFINITIONS
────────────────────

ROLE: GUEST (Unauthenticated)
Responsibilities: Browse public listings, view basic seller info
Permissions:
  - GET /api/v1/listings (public fields only)
  - GET /api/v1/listings/{id} (public view)
  - GET /api/v1/categories
  - POST /api/v1/auth/register
  - POST /api/v1/auth/login
Dashboard: None (redirect to login for protected actions)
Security: Rate limited 30 req/min, no PII access

ROLE: BUYER
Responsibilities: Browse, search, negotiate, purchase materials
Permissions:
  - All Guest permissions
  - GET /api/v1/listings/search (full search with filters)
  - POST /api/v1/conversations (initiate chat with seller)
  - GET/POST /api/v1/conversations/{id}/messages
  - POST /api/v1/transactions (create purchase order)
  - GET /api/v1/transactions/my (as buyer)
  - POST /api/v1/payments/initiate
  - POST /api/v1/payments/{id}/confirm
  - POST /api/v1/ratings (rate seller after transaction)
  - GET /api/v1/sellers/{id}/profile
  - POST /api/v1/watchlist
  - GET /api/v1/notifications
  - PUT /api/v1/users/me
Dashboard:
  - Browse/Search Listings (grid/map view)
  - My Watchlist
  - My Conversations
  - My Transactions (buyer view)
  - Payment History
  - Ratings Given
Security: JWT required, MFA optional, rate limit 100 req/min

ROLE: SELLER
Responsibilities: Create listings, manage inventory, fulfill orders
Permissions:
  - All Buyer permissions
  - POST /api/v1/listings (create new listing)
  - PUT/DELETE /api/v1/listings/{id} (edit/delete own listings)
  - GET /api/v1/listings/my (seller's own listings)
  - PUT /api/v1/transactions/{id}/accept/reject/ship
  - GET /api/v1/analytics/sales
  - GET /api/v1/payments/escrow
  - POST /api/v1/verification/request
Dashboard:
  - My Listings (CRUD, analytics)
  - Sales Analytics (revenue, views, conversion)
  - Incoming Orders (accept/reject/ship)
  - Escrow Status (pending releases)
  - Verification Requests
  - Seller Rating & Reviews
Security: JWT + phone verified, listing value limits for new sellers
Approval: Auto-approved for listings < 10,000 ETB, manual for higher

ROLE: VERIFICATION_AGENT
Responsibilities: Physically inspect listings, verify quality/quantity
Permissions:
  - GET /api/v1/verification/assigned
  - GET /api/v1/verification/{id}
  - POST /api/v1/verification/{id}/submit
  - POST /api/v1/verification/{id}/photos
  - GET /api/v1/listings/{id} (full details)
  - PUT /api/v1/verification/{id}/status
Dashboard:
  - Assigned Inspections Queue
  - Inspection Form (photos, GPS, notes, condition grade)
  - Inspection History
  - Performance Metrics (inspections/day, accuracy score)
Security: GPS tracking during inspections, photo EXIF verification
Approval: Background check + training + NDA required

ROLE: DELIVERY_AGENT
Responsibilities: Pick up and deliver materials, capture signatures
Permissions:
  - GET /api/v1/delivery/assigned
  - PUT /api/v1/delivery/{id}/accept/pickup/deliver
  - GET /api/v1/delivery/history
  - POST /api/v1/delivery/{id}/signature
Dashboard:
  - Available Delivery Jobs (nearby, with earnings)
  - Active Deliveries (GPS tracking, route)
  - Delivery History & Earnings
  - Performance Rating
Security: Vehicle inspection required, insurance verification
Approval: Vehicle docs + insurance + background check

ROLE: ADMIN
Responsibilities: Moderate content, handle disputes, manage users
Permissions:
  - All Buyer/Seller permissions
  - GET/PUT /api/v1/admin/users
  - GET/PUT /api/v1/admin/listings
  - GET/PUT /api/v1/admin/transactions
  - GET/PUT /api/v1/admin/verification
  - GET /api/v1/admin/reports
  - GET /api/v1/admin/audit-logs
Dashboard:
  - User Management (CRUD, suspend, roles)
  - Listing Moderation (approve, flag, remove)
  - Transaction Monitoring (disputes, refunds)
  - Verification Queue Management
  - Analytics & Reports (KPIs, revenue, growth)
  - Audit Logs (immutable, searchable)
Security: MFA mandatory, IP whitelist, session timeout 15min
Approval: Internal hire only, background check, dual-auth for sensitive

ROLE: SUPER_ADMIN
Responsibilities: System configuration, agent onboarding, financial ops
Permissions:
  - All Admin permissions
  - POST/PUT /api/v1/admin/agents
  - GET /api/v1/admin/finance/reconciliation
  - POST /api/v1/admin/escrow/release (requires dual auth)
  - GET/PUT /api/v1/admin/system/config
  - GET/PUT /api/v1/admin/commission/settings
  - GET/POST /api/v1/admin/backups
Dashboard:
  - Agent Onboarding & Management
  - Financial Operations (reconciliation, escrow release)
  - System Configuration (feature flags, rates)
  - Commission Settings
  - Backup & Disaster Recovery
  - API Keys & Integrations
Security: MFA mandatory, hardware token preferred, dual-auth all financial
Approval: C-level only, 4-eyes principle for all financial operations

              -> DISPUTED -> RELEASED/REFUNDED

-- ============================================================
-- CORE TABLES
-- ============================================================

CREATE TABLE users (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    phone_number        VARCHAR(20) NOT NULL UNIQUE,
    email               VARCHAR(255) UNIQUE,
    password_hash       VARCHAR(255) NOT NULL,
    full_name           VARCHAR(255) NOT NULL,
    company_name        VARCHAR(255),
    tin_number          VARCHAR(50),
    business_license    VARCHAR(255),
    profile_image_url   VARCHAR(500),
    role                VARCHAR(50) NOT NULL DEFAULT 'BUYER' 
                        CHECK (role IN ('GUEST','BUYER','SELLER','VERIFICATION_AGENT','DELIVERY_AGENT','ADMIN','SUPER_ADMIN')),
    status              VARCHAR(20) NOT NULL DEFAULT 'PENDING_VERIFICATION' 
                        CHECK (status IN ('PENDING_VERIFICATION','ACTIVE','SUSPENDED','BANNED','DELETED')),
    kyc_status          VARCHAR(20) NOT NULL DEFAULT 'UNVERIFIED'
                        CHECK (kyc_status IN ('UNVERIFIED','PENDING','VERIFIED','REJECTED')),
    mfa_enabled         BOOLEAN DEFAULT FALSE,
    mfa_secret          VARCHAR(255),
    failed_login_attempts INTEGER DEFAULT 0,
    locked_until        TIMESTAMP,
    last_login_at       TIMESTAMP,
    last_login_ip       INET,
    email_verified      BOOLEAN DEFAULT FALSE,
    phone_verified      BOOLEAN DEFAULT FALSE,
    rating_avg          DECIMAL(2,1) DEFAULT 0.0 CHECK (rating_avg >= 0 AND rating_avg <= 5),
    rating_count        INTEGER DEFAULT 0,
    total_transactions  INTEGER DEFAULT 0,
    created_at          TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMP NOT NULL DEFAULT NOW(),
    deleted_at          TIMESTAMP,
    created_by          UUID REFERENCES users(id),
    updated_by          UUID REFERENCES users(id)
);

CREATE INDEX idx_users_phone ON users(phone_number);
CREATE INDEX idx_users_role ON users(role);
CREATE INDEX idx_users_status ON users(status);
CREATE INDEX idx_users_kyc ON users(kyc_status);
CREATE INDEX idx_users_created_at ON users(created_at);

-- LISTINGS

CREATE TABLE listings (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    seller_id           UUID NOT NULL REFERENCES users(id),
    title               VARCHAR(255) NOT NULL,
    description         TEXT NOT NULL,
    category_id         UUID NOT NULL REFERENCES categories(id),
    condition           VARCHAR(20) NOT NULL 
                        CHECK (condition IN ('NEW','LIKE_NEW','GOOD','FAIR','SALVAGE')),
    quantity            DECIMAL(15,3) NOT NULL,
    unit                VARCHAR(50) NOT NULL,
    price_per_unit      DECIMAL(15,2) NOT NULL,
    total_price         DECIMAL(15,2) NOT NULL,
    currency            VARCHAR(3) NOT NULL DEFAULT 'ETB',
    is_negotiable       BOOLEAN DEFAULT TRUE,
    min_price           DECIMAL(15,2),
    location_id         UUID REFERENCES locations(id),
    address             TEXT,
    latitude            DECIMAL(10,8),
    longitude           DECIMAL(11,8),
    geo_point           GEOGRAPHY(POINT,4326),
    status              VARCHAR(20) NOT NULL DEFAULT 'DRAFT'
                        CHECK (status IN ('DRAFT','PENDING_APPROVAL','ACTIVE','SOLD','EXPIRED','REJECTED','SUSPENDED','DELETED')),
    verification_status VARCHAR(20) NOT NULL DEFAULT 'UNVERIFIED'
                        CHECK (verification_status IN ('UNVERIFIED','PENDING','VERIFIED','REJECTED')),
    view_count          INTEGER DEFAULT 0,
    inquiry_count       INTEGER DEFAULT 0,
    expires_at          TIMESTAMP NOT NULL,
    featured_until      TIMESTAMP,
    is_featured         BOOLEAN DEFAULT FALSE,
    tags                TEXT[],
    metadata            JSONB,
    created_at          TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMP NOT NULL DEFAULT NOW(),
    published_at        TIMESTAMP,
    deleted_at          TIMESTAMP
);

CREATE INDEX idx_listings_seller ON listings(seller_id);
CREATE INDEX idx_listings_category ON listings(category_id);
CREATE INDEX idx_listings_status ON listings(status);
CREATE INDEX idx_listings_verification ON listings(verification_status);
CREATE INDEX idx_listings_geo ON listings USING GIST(geo_point);
CREATE INDEX idx_listings_price ON listings(price_per_unit);
CREATE INDEX idx_listings_created ON listings(created_at);

-- ============================================================
-- CONVERSATIONS & MESSAGES
-- ============================================================

CREATE TABLE conversations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    listing_id      UUID REFERENCES listings(id),
    buyer_id        UUID NOT NULL REFERENCES users(id),
    seller_id       UUID NOT NULL REFERENCES users(id),
    status          VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
                    CHECK (status IN ('ACTIVE','BLOCKED','ARCHIVED')),
    last_message_at TIMESTAMP,
    unread_count_buyer INTEGER DEFAULT 0,
    unread_count_seller INTEGER DEFAULT 0,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    UNIQUE(listing_id, buyer_id, seller_id)
);

CREATE INDEX idx_conversations_buyer ON conversations(buyer_id);

6.1 ARCHITECTURE DECISION: MICROSERVICES
────────────────────────────────────────
DECISION: Use Microservices Architecture (not monolith or modular monolith)

REASONING:
- Each service can scale independently (payment service needs more resources)
- Different teams can work on different services
- Technology flexibility (can use different languages if needed)
- Fault isolation (one service down doesn't bring down everything)
- Independent deployment (faster release cycles)

TRADE-OFFS:
- Operational complexity (monitoring, tracing)
- Network latency between services
- Data consistency challenges
- Higher initial development cost

MITIGATION:
- Use service mesh (Istio) for observability
- Event-driven architecture for eventual consistency
- API Gateway for unified client interface
- Shared libraries for common concerns

ASYNC (Kafka Events):

- Listing created -> Search Service (index), Notification Service (alerts)
- Payment completed -> Transaction Service (update state), Notification Service
- Escrow released -> Payment Service (transfer to seller)
- Verification completed -> Listing Service (add "verified" badge)

CQRS (Command Query Responsibility Segregation):
- Write: PostgreSQL (ACID transactions)
- Read: Elasticsearch (search, analytics), Redis (hot data)

SECTION 7: SECURITY
═══════════════════════════════════════════════════════════════════════════════

7.1 AUTHENTICATION & AUTHORIZATION
──────────────────────────────────
- JWT Tokens:
  - Access token: 15 minutes expiry
  - Refresh token: 7 days expiry, stored in httpOnly cookie
  - Algorithm: RS256 (asymmetric, private key on server)
  - Claims: userId, role, permissions, issuedAt, expiresAt

- Multi-Factor Authentication:
  - SMS OTP (primary for Ethiopian market)
  - TOTP (Google Authenticator) as secondary
  - Mandatory for Admin/SuperAdmin roles
  - Optional for Seller roles (recommended)

- Session Management:
  - Redis-backed sessions
  - Session invalidation on password change
  - Concurrent session limit (max 3 per user)
  - Device fingerprinting for anomaly detection

7.2 ENCRYPTION
──────────────
- In Transit: TLS 1.3 minimum, HSTS enabled
- At Rest:
  - Database: AES-256-GCM (pgcrypto extension)
  - File Storage: Server-side encryption (MinIO)
  - Backups: Encrypted before upload
- Field-Level:
  - Phone numbers: AES-256-GCM
  - Bank details: AES-256-GCM
  - ID numbers: AES-256-GCM
  - KYC documents: AES-256-GCM
- Passwords: BCrypt with cost factor 12
- API Keys: SHA-256 hashed in database

7.3 API SECURITY
────────────────
- Rate Limiting:
  - Guest: 30 req/min per IP
  - Authenticated: 100 req/min per user
  - Payment endpoints: 10 req/min per user
  - Admin endpoints: 50 req/min per admin

- Input Validation:
  - Jakarta Validation on all DTOs
  - SQL injection prevention (parameterized queries)
  - XSS prevention (OWASP Java Encoder)
  - CSRF tokens for state-changing operations
  - File upload restrictions (images only, max 5MB)

- Output Encoding:
  - All user-generated content encoded before display
  - Content Security Policy (CSP) headers
  - X-Frame-Options: DENY
  - X-Content-Type-Options: nosniff

7.4 AUDIT & COMPLIANCE
──────────────────────
- Immutable Audit Logs:
  - Who, what, when, from which IP
  - 7-year retention (tax/legal compliance)
  - Separate database, write-once access
  - Partitioned by month for performance

- Data Protection (Ethiopian ECA compliance):
  - Consent management for data collection
  - Right to access (user can download their data)
  - Right to deletion (soft delete with 30-day grace)
  - Data minimization (collect only what's needed)
  - Breach notification within 72 hours

7.5 DISASTER RECOVERY
─────────────────────
- Backup Strategy:
  - Database: Every 6 hours (incremental), daily (full)
  - Files: Every 24 hours
  - Retention: 30 days local, 90 days offsite
  - Test restore: Monthly

- RTO/RPO:
  - Recovery Time Objective (RTO): < 4 hours
  - Recovery Point Objective (RPO): < 1 hour

- Multi-Region:
  - Primary: Addis Ababa (Ethio Telecom Cloud)
  - Secondary: Hawassa (async replication)
  - Failover: Manual with automated scripts

7.6 OWASP TOP 10 MITIGATION
─────────────────────────────
A01: Broken Access Control    -> RBAC + JWT validation + API Gateway
A02: Cryptographic Failures   -> AES-256-GCM + TLS 1.3 + BCrypt
A03: Injection                -> Parameterized queries + ORM
A04: Insecure Design          -> Threat modeling + security review
A05: Security Misconfiguration-> Immutable infrastructure + config validation
A06: Vulnerable Components    -> Snyk/Dependabot scanning
A07: Auth Failures            -> MFA + session management + lockout
A08: Data Integrity Failures  -> Digital signatures + checksums
A09: Logging Failures         -> Centralized logging + tamper detection
A10: SSRF                     -> URL validation + network policies

SECTION 11: PERFORMANCE OPTIMIZATION
═══════════════════════════════════════════════════════════════════════════════

11.1 CACHING STRATEGY
─────────────────────
Layer 1: Browser Cache (static assets, images)
Layer 2: CDN Cache (images, static content)
Layer 3: Redis Cache (sessions, hot listings, search results)
Layer 4: Application Cache (in-memory, computed data)
Layer 5: Database Cache (query results, connection pool)

Cache Keys:
- listings:hot:{category} -> Top 100 listings per category
- listings:detail:{id} -> Listing details (TTL: 5 min)
- search:results:{hash} -> Search results (TTL: 2 min)
- user:profile:{id} -> User profile (TTL: 10 min)
- categories:all -> All categories (TTL: 1 hour)

Cache Invalidation:
- Write-through: Update cache on DB write
- TTL-based: Automatic expiration
- Event-driven: Kafka events trigger cache invalidation

11.2 DATABASE OPTIMIZATION
──────────────────────────
- Indexes: All foreign keys, search fields, sort fields
- Partitioning: audit_logs by month, messages by conversation
- Query Optimization: EXPLAIN ANALYZE on slow queries
- Connection Pooling: HikariCP (max 20 connections)
- Read Replicas: 2 replicas for read-heavy workloads
- Query Result Caching: Redis for frequent queries
- Batch Operations: Bulk inserts/updates where possible

11.3 IMAGE OPTIMIZATION
───────────────────────
- Format: WebP with JPEG fallback
- Compression: 80% quality for photos, 90% for thumbnails
- Responsive Images: Multiple sizes (200px, 400px, 800px)
- Lazy Loading: Images load on scroll
- CDN: Cloudflare or local CDN for global delivery
- Watermark: Automatic watermark on upload

11.4 BACKGROUND JOBS
────────────────────
Framework: Quartz Scheduler + Spring Batch
Jobs:
- Listing expiration check (every hour)
- Escrow auto-refund (daily at midnight)
- Commission calculation (daily)
- Reconciliation report generation (daily)
- Image processing (on upload)
- Notification batch sending (every 5 minutes)
- Audit log archiving (monthly)
- Database backup (every 6 hours)

11.5 QUERY OPTIMIZATION
───────────────────────
- N+1 Query Prevention: JOIN FETCH, EntityGraph
- Pagination: Cursor-based for large datasets
- Projection: Select only needed columns
- Batch Fetching: @BatchSize on collections
- Native Queries: For complex aggregations
- Materialized Views: For analytics dashboards

11.6 HORIZONTAL SCALING
───────────────────────
- Kubernetes HPA: 2-20 pods per service
- Database Sharding: By user ID for future scale
- Read Replicas: 1 primary + N replicas
- CDN: Global edge caching
- Message Queue: Kafka partitioning by key

production-ready, scalable, and secure marketplace platform for the Ethiopian
construction industry.
